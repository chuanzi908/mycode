# 四人答辩报告与实验取证建议

这是写作和工作分配建议，不是老师已经批准的目录或页数。老师要求四人每人不少于 15 页，应先确认学校对封面、目录、参考文献、完整代码附录和重复内容是否计入每人页数的规定。不要靠重复代码、空图或虚构实验凑页数。

## 建议分工：每人规划至少 16 页独立内容

| 成员 | 主责 | 可展开的独立内容 | 代码和证据 |
|---|---|---|---|
| 1：网络原理与总体设计 | 需求、TUN 数据路径、IPv4/TCP 与状态机 | 问题背景、场景、协议首部、伪首部校验和、三次握手、序号/确认号、状态转换、安全及限制、总体架构 | 架构图、时序图、首部字段表、抓包说明 |
| 2：协议栈实现（项目实体） | `stack.py`、客户端和 Linux 演示 | TUN 创建、输入校验、连接表、报文构造、ACK、重传、FIN、超时、关键代码解析、运行和故障排查 | 命令、Linux 实测截图、pcap 及字段解释、单元测试 |
| 3：测试与实验 | 单包及状态序列模糊测试 | 测试建模、算子、随机种子、不变量、状态事件、样例重放、对照实验、数据分析、有效性威胁 | `fuzz.py`、`agent_fuzz.py`、`experiment.py`、原始 JSON/CSV |
| 4：大模型与项目整合 | 模型接口、策略反馈、结果与答辩 | 智能体流程、提示和 JSON 验证、接口与密钥、对照实验、失败处理、伦理与限制、团队集成、展望 | 实际模型调用截图、模型名和参数、日志、图表 |

每人按 16 页规划共有约 64 页独立内容；具体排版后页数可能不同，要以老师口径为准。完整代码可以作为统一附录，同时正文逐模块解释关键实现；不要把尚未实现的功能写成已实现。

## 实验记录表模板

每次实验记录：项目版本或压缩包哈希、日期、操作系统和 Python 版本、命令、权限、随机种子、测试预算、实际输出、退出码、截图文件名、原始结果文件、异常和复现步骤。大模型实验另记服务商、模型名、实际提示、参数、策略权重、接口错误及是否成功调用；密钥不写进报告或截图。

## 最小证据清单

1. Linux 实测：服务启动、客户端回显、三次握手和关闭的 pcap、退出统计；保留 `integration-output` 目录。
2. 正确性：自动测试结果及每项测试验证的性质。
3. 模糊测试：种子、算子和数量、JSON、失败重放；无失败时明确说未发现，不编造漏洞。
4. 对照实验：相同预算、多个种子、每轮权重和事件表；说明观测点不是代码覆盖率、相同种子不保证两种策略输入完全相同。
5. 大模型：实际服务调用后的提示、输出权重及结果，不能将本地模拟或离线规则描述为真实调用。
6. 分工：每人实际贡献、文件版本和个人负责页码，提交前由全组核对。

## 可能的答辩问题

- TUN 与 TAP 的数据单位有何区别？本项目选择了哪一种，为什么不需要处理以太网和 ARP？
- TCP 校验和为何包含伪首部？如何处理奇数字节？SYN 和 FIN 为什么消耗序号？
- 正常握手和关闭的每一步分别推进什么状态和序号？抓包能否对应代码？
- 当前实现为什么不是完整 TCP？拥塞控制、乱序重组和 TIME_WAIT 缺失有什么影响？
- 与随机单包相比，状态序列测试可以触及什么行为？自定义事件能否等同于代码覆盖率？
- 大模型实际改变了什么？当模型接口出错或 JSON 不合法时如何处理？对照实验能支持什么结论？

参考文献应由小组核实后填写真实书籍、RFC 和工具资料，不要编造来源。格式、字体和行距以老师提供的原始模板为准。
